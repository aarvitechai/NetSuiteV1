# Test strategy (Phase 12)

## Test pyramid

| Level | Scope | Where | Runs on | Count* |
|---|---|---|---|---|
| **Unit** | Pure rules: money, state machines, eligibility, NACHA, parsers, matching, retry, idempotency, config, SuiteQL binding | `middleware/tests/unit`, `netsuite/tests/rules.test.ts` | Every commit (CI) | ~140 |
| **SuiteScript behaviour** | Each script type, run against fake `N/*` modules | `netsuite/tests/scripts.test.ts` | Every commit | 17 |
| **Contract** | Upstream mapping, NetSuite REST adapter (fake fetch), SDF objects ↔ code, middleware ↔ SuiteScript rule parity, Store implementations (memory and PostgreSQL) | `middleware/tests/contract`, `netsuite/tests/*objects*`, `unit/store.test.ts`, `unit/netsuite-adapters.test.ts` | Every commit. PostgreSQL runs when `TEST_DATABASE_URL` is set (always in CI) | ~45 |
| **API / integration** | HTTP routes plus services plus simulators (bank, payment provider) plus the mock NetSuite | `middleware/tests/api` | Every commit | ~62 |
| **Reliability and security** | Outbox crash recovery, failure injection, rate limit, headers, log redaction, secret rotation | `middleware/tests/reliability` | Every commit | 10 |
| **End to end** | A full accounting period across AP, AR, bank and NetSuite, with control totals | `middleware/tests/e2e` | Every commit | 2 |
| **Performance** | Volume run of every stage | `npm run loadtest` | Before release; numbers in `docs/performance/report.md` | — |
| **UAT** | Finance-style scenarios run by people | `docs/testing/uat-scripts.md` | Before each production release | 10 scripts |

\*See `docs/testing/test-report.md` for the exact numbers from the last run.

## Principles

- **Deterministic.** A fixed clock (2026-11-20), synthetic seed data, no network, and a fresh SFTP
  temp folder per test. The same input always gives the same result.
- **Test behaviour through public interfaces** (HTTP, service methods), not private internals.
- **Every bug gets a test first.** See the defect log. Each defect has the test that now guards it.
- **Failure paths are first-class.** Every scenario in the plan has an automated test: duplicate bill,
  rejected payment, returned ACH, timeout, partial batch failure, duplicate webhook, refund,
  chargeback, fee deduction, unmatched line.

## Which tests require a real NetSuite sandbox?

The automated suite proves our logic against **simulators**. These must be repeated in a sandbox:

| Area | Why the mock cannot prove it |
|---|---|
| SuiteTalk REST request bodies (`apply.items`, `cashBack`, `currency.refName`), the `eid:` upsert, SuiteQL field names | Only NetSuite validates the real schema |
| TBA authentication end to end | It needs a real integration record and token |
| SuiteScript governance consumption, `getFields()` on XEDIT, Map/Reduce formula column naming | Platform behaviour |
| SuiteFlow workflows W1–W9 | They are built in the UI |
| SDF deploy (`project:validate`, `project:deploy`) | Account-specific objects and features |
| Concurrency limits and 429 behaviour under load | Account-specific limits |
| Closed accounting period errors and their exact error text | Account configuration |

The sandbox checklist is in `docs/access-checklist.md`. Record what was run in `KNOWN_LIMITATIONS.md`.

## Regression policy

- `npm run ci` (lint, format, typecheck, all tests) runs on every push and pull request (Phase 13), and
  must be green before promoting `dev → staging → production → main`.
- After any change to **scripts, workflows, API or mappings**:
  1. The automated suite covers the logic.
  2. Re-run the UAT scripts that touch the changed area (the mapping table at the bottom of
     `uat-scripts.md`).
  3. Re-run the sandbox checks above for any NetSuite-facing change.

## Exit criteria for UAT

1. Every UAT script has passed and been signed off.
2. No open defect of severity 1 or 2.
3. The period control totals are balanced (`GET /reconciliation/control-totals` returns
   `balanced: true`) for the UAT period.
4. A qualified accounting reviewer has signed off the accounting mappings
   (`docs/accounting-mappings/accounting-event-matrix.md`).

## How do we prove no transaction was lost or duplicated?

- **The control-totals report.** Its nine checks compare counts *and* amounts across bills,
  instructions, NetSuite payments and bank lines.
- **The reconciliation report.** It shows zero open exceptions and zero unreconciled NetSuite
  transactions.
- **The DLQ and outbox are empty.** `GET /ops/dashboard` shows nothing stuck.
